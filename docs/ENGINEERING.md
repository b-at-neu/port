# Engineering Standards

Every pipeline agent reads this document before working. It defines the quality bar beyond what is obvious from the code. Plans must account for it per feature, implementations must follow it, and review findings may cite its sections the same way they cite the plan.

This is **this repository's own** standards document, not a template — `plugins/port/templates/ENGINEERING.template.md` is the skeleton `/port:init` installs elsewhere. Concrete paths like `plugins/port/**` are therefore correct here, and only here.

**Where things live is not this document's job.** [ARCHITECTURE.md](../ARCHITECTURE.md) is the canonical repository map and the authority on the ship boundary; it carries its own layer 1 pin (`scripts/checks.ts` → "Repository map covers the real tree, both directions"), so restating its table here would create a second copy with nothing pinning it — exactly what §2 forbids. This document covers *how* to write, not *where* to put it.

**Citations name checks and sections, never line numbers.** `scripts/checks.ts` and `docs/PIPELINE.md` are the two most-churned files in the repository, so a line reference in either is stale within days. Every citation below names a `// --- ` check block or a markdown heading, both of which survive edits and file splits.

**Stack:** Markdown agent and skill definitions (the product) · Node.js ESM scripts in TypeScript, type-stripped at load with zero runtime dependencies (static checks, artifact validation, worktree reclamation), at or above `package.json`'s `engines.node` floor · JSON Schema draft 2020-12 · GitHub Actions · `gh` CLI for all GitHub I/O · a pnpm workspace with TypeScript and Electron (`apps/desktop`)

## 1. Architecture

`plugins/port/docs/PIPELINE.md` is the single source of truth for operating rules, the label lifecycle, the permission model, and every output format. Every agent and skill references it and restates **only** what is unique to itself. A rule belonging to more than one stage goes there, not into each stage — and when it must appear in several files, it goes in as a byte-identical block with a pin (see §2).

### Rules

**Hook and script code separates pure decision logic from I/O.** `hooks/lib/guard-rules.mjs` exports pure functions unit-tested directly; `hooks/agent-guard.mjs` is the thin stdin/stdout/exit-code wrapper, tested separately by spawning the real script ("Guard hook classifier" and "Guard hook end-to-end wiring"). The same split applies to the worktree reclamation script ("Worktree reclamation classifier"). New logic goes in the library, not the wrapper — the wrapper's tests cannot see a classifier bug and the classifier's tests cannot see a wiring bug.

**Scripts follow one runnable entry point plus a shared library.** `scripts/checks.ts` is a runner that only wires — it discovers and imports every `scripts/checks/<topic>.ts` module from disk, awaits each in turn, then calls `report()`, with no assertions and no hand-maintained module list of its own. Each topic module exports a function taking the reporter, typed `Reporter` (`scripts/lib/report.ts`). `scripts/lib/report.ts` is a deliberately dumb collector and printer, shared by layers 1 and 2, which "decides nothing" (its own header); `scripts/lib/files.ts` holds the file-system helpers (`root`, `readJson`, `walk`, `frontmatter`) the topic modules share. A new check goes into the topic module it belongs to, never into the runner — nearly every ticket adds a regression guard, so a runner that reabsorbed assertions directly would recreate the file-contention bottleneck the split exists to remove (`PIPELINE.md:95-114`). Source is type-stripped, never type-checked at runtime: `scripts/lib/errors.ts`'s `message(e: unknown): string` is the one helper every `catch` site imports rather than casting `e` by hand, and JSON read off disk (`readJson`) stays `any` — a port config's shape and defaults come from `schema/port.config.schema.json`, never a hand-transcribed TypeScript interface (§2's own rule, restated for `scripts/` specifically).

**The trajectory record is write-only from the tick engine's own decision path.** `scripts/port-tick/events.ts` (the emitter) exports no function whose name contains `read` or `parse`, and nothing under `scripts/port-tick/` besides `port-tick.ts` and `report.ts` itself may import `events.ts` or `report.ts` ("Write-only rail", `scripts/checks/tick-events.ts`) — an append-only history that fed a future tick's decision would quietly break `plan`'s own never-persists invariant (#203).

**A file that an adopting repository copies alone must be self-contained.** `plugins/port/bin/artifacts.mjs`, `bin/worktrees.mjs`, and `bin/budget.mjs` carry no relative imports, because an import resolving only inside this checkout breaks silently for every adopter while passing here — checked directory-wide, not per file ("bin/ holds only self-contained .mjs", `scripts/checks/layout.ts`). Cross-platform behaviour is part of the same contract — these run on an adopter's Windows machine, not just this one, which is why `bin/worktrees.mjs` and `bin/budget.mjs` also carry their own `execSync`/`shell: true` bans in `scripts/checks/cockpit.ts` and `scripts/checks/budget.ts`. This is also why §7's line limit exempts `bin/` instead of splitting it: the runner-plus-modules split every other over-limit file uses would break this same self-containment guarantee (#183).

**`plugins/port/` is one contract per directory (#171).** `templates/` holds only fill-in templates a `/port:init` or `/port:analyze` run substitutes into; `bin/` holds only self-contained executables copied verbatim into a managed repository, some of which this repository also runs in place; `data/` holds only canonical data — currently `labels.json` alone. `scripts/checks/layout.ts` pins all three, plus the absence of any tracked file still naming one of the three moved files under its old `templates/`-relative path.

**No repository-specific value is ever a literal in prompt text.** Label names, check names, branch names, and the repository slug are resolved from `.claude/port.config.json` or from PIPELINE.md's default table at read time. A literal label name silently matches nothing — `gh issue list --label <unknown>` exits 0 with an empty result — and a literal CI check name breaks the moment a repository renames its workflow job ("No config key appears as a literal --label argument", "Generality guard — no literal CI check name in a stage prompt"). The test to apply: **would this behave correctly in a freshly `/port:init`-ed repository with renamed labels, a single branch, and a different set of CI checks?**

**Anything shipped may only reference other shipped paths.** A reference from a file under `plugins/port/` to a repository-only doc or script — `docs/USAGE.md`, `CONTRIBUTING.md`, `scripts/checks.ts` — dangles in every adopter's plugin cache, which carries only `plugins/port/` (`scripts/checks.ts` → "Shipped references stay inside plugins/port/").

### Module boundaries

Sorted ascending by the path each paragraph opens with — a new boundary is inserted at its alphabetical slot, never appended at the end, so two tickets adding one each land at different offsets and git merges both (#255).

**`apps/desktop/src/main/actions/` is the app's only `applyLabels` caller** — pause/resume/retry/gate (#94), the first wiring of #90's write chokepoint into the app, joined by the plan gate's own answer and the claim dialog's own write (#92, retiring the grandfathered second-caller exception this paragraph used to record). `shared/actions/plan.ts`'s `actionsFor` derives, purely, which of the four single-label actions an item offers and what each one's key-level plan is; `main/actions/apply.ts`'s `applyItemAction` rebuilds the `LabelWriteRequest` from the watcher's own snapshot and the registry's vocabulary, never from anything the renderer sent — a renderer-supplied `expectedStage` is only ever grounds to refuse, never to widen a plan. `main/actions/resume.ts`'s `recoverPausedTrigger` is the one exception a pure plan cannot resolve: the trigger a pause removed is read back off `writes.jsonl` (`pausedTriggerFrom`, the inverse of the pause plan's own `expect.present`), never guessed. `main/actions/claim.ts`'s `applyClaimLabels` is a direct pass-through `main/claim.ts` calls instead of reaching `main/writes/` itself — behaviour-identical to what it replaced, existing only to retire the exception. `main/actions/gate.ts` is the plan gate's own composition root (#92): it resolves the `ready` registry entry the same way `main/claim.ts` does, splits the fetched issue body at `IMPLEMENTATION_PLAN_HEADING` (`main/state/link.ts`'s own `sessionRequiredMarkerAt`, never re-derived), classifies through `shared/gate/classify.ts`, and reads the plan-gate claim through `main/writes/`'s `readGateClaim`. Its own `gateAnswer` follows a fixed order — classify, then (for `request-changes`) `postComment`, then `applyLabels` — so a feedback comment always lands before the label swap that would move the item off `plan review`, never after. `main/actions/escalate.ts`'s `escalateToHuman` (#293) is a second, deliberately generic composition over the same two writers — swap first (`applyLabels`, adding `needsHuman` and removing the caller's own trigger), then comment only when that swap actually applied, the opposite order from `gateAnswer`'s comment-before-swap: a failed comment still leaves the item stopped, and a failed swap never posts a comment that would repeat on every poll. The budget gate (`main/dispatch/`) calls this one function rather than growing a third `applyLabels`/`postComment` pair. **`main/actions/observe.ts`'s `applyObservation` (#292) is a fourth, sibling composition over the same two writers, for the four machine-observation write families `main/tick/observe.ts` computes** (liveness resets, cycle-cap/zero-diff escalation, the refresh sweep, approval withdrawal) — generic enough to cover all four, since none of them share `escalateToHuman`'s fixed trigger-to-`needsHuman` shape (a refresh adds `refreshBranch` without removing anything; withdrawal swaps `approved` for `needsRevision`, not a trigger). Swap first, then (only on `applied`, and only when the plan carries one) the comment — the same swap-then-comment ordering `escalateToHuman` already follows. The write plan itself (`add`/`remove`/`expect`/`action`/`comment`) comes from `main/dispatch/observation.ts`'s pure `observationWrite`, mirroring `scripts/port-tick/writes.ts`'s own label tables; every request names `requiredScopes: ['dispatch']`, so `applyLabels` refuses a losing writer the moment the claim moves mid-pass. The `desktop-actions` layer 1 check pins the `RETRY_TRIGGER` copy against `scripts/port-tick/liveness.ts`, the caller boundary (now with no exception left), the absence of a literal label name outside a test file, and the ungated selection's own dependency on `approvalGate`; `desktop-gate` pins the plan gate's own rails, including the comment-before-swap ordering, and `escalate.ts`'s and `observe.ts`'s own swap-before-comment ordering alongside it.

**`apps/desktop/src/main/channels/<topic>.ts` holds one topic's worth of IPC channel validation and composition; `main/ipc.ts` stays the registrar.** Two pre-existing files sat exactly at the 500-line ratchet with nowhere left to register the plan gate's four new channels (#92), so `main/channels/sessions.ts` took the sessions/transcript/search resolvers (a pure relocation, no behaviour change) and `main/channels/gate.ts` took the gate's own four, both following every other channel's own `*Deps` injectable-seam idiom. The remaining resolvers still in `main/ipc.ts` move out the same way as each is next touched, never all at once in a ticket that has no reason to.

**`apps/desktop/src/main/claim.ts` is the claim dialog's only composition root** ("work on #N" from the UI, #93) — it resolves the `ready` registry entry, calls `main/github/`'s `fetchClaimPreflight`, runs the pure `shared/claim/classify.ts` (`classifyPreflight`/`buildClaimRequest`), and — for `claimApply` only — hands the result to `main/writes/`'s `applyLabels`. It re-runs the preflight itself on apply rather than trusting anything the renderer held, and refuses `moved` before ever building a request when a fresh assignee read disagrees with what the operator confirmed. No `gh` import lives here; the read comes from `./github`, the write from `./writes`. The `desktop-claim` layer 1 check pins the `blockedBy`/`viewer` selection boundary, the absence of the `'@me'` sentinel, the `expect.absent` guard, and the opt-in key set against `plugins/port/skills/pipeline/SKILL.md`'s own paragraph.

**`apps/desktop/src/main/dispatch/` owns the app-wide drain switch and the halt composition over it (#110).** `store.ts`'s `createDrainStore` is a durable switch over `<userData>/dispatch.json`, the same read/version-gate/atomic-write idiom `main/registry/store.ts` already follows for `registry.json` — `current()` stays synchronous and starts `{ gate: 'draining', reason: 'unread' }` so a not-yet-`load()`-ed store never reads as open, and the literal `{ gate: 'open' }` is constructed exactly once (`OPEN`), reused everywhere else, so a later failure path cannot quietly fail open by retyping it. `main/tick/dispatchable.ts`'s `dispatchableFrom` is the sole function that turns a `TickReport` into a set anything may act on — `report.actionable` keeps reporting the full set while draining (ENGINEERING §4: fails closed on actions, never on reporting), and only `dispatchableFrom` yields `[]` for it, so #106's own dispatcher must consume the gate rather than re-deriving it. `halt.ts`'s `haltDispatch` is drain-then-stop-every-claim: `drain.set(true)` runs first and a failed write aborts the whole call before a single label is touched, then every in-flight item across every ready repository is visited sequentially through `main/actions/`'s own `applyItemAction` with `action: 'stop'` — never a second `applyLabels` caller. `resolve.ts`'s `resolveDispatchControl` is the `dispatch:control` channel's own composition root, validating `command` against `DISPATCH_COMMANDS` by name. `stop` itself is a fifth `OperatorAction` (`shared/actions/plan.ts`'s `stopPlan`) beside pause/resume/retry/gate: it removes an in-flight label and adds nothing, so `resume`'s own `recoverPausedTrigger` (`main/actions/resume.ts`) widens to read a `stop` entry off the audit log too, mapping an in-flight key forward through `RETRY_TRIGGER` before it becomes a trigger `resume` can restore. **`dispatcher.ts`'s `createDispatcher` (#265) is the composition root for the app dispatching a pipeline stage in place of the cockpit.** It reads the gate claim (`readGateClaim`) each tick to decide ownership (`'app'` only when the claim holds `dispatch` or is unreadable, `'cockpit'` otherwise — the same fail-claimed direction `planGateDenial`/`dispatchDenial` already take), and otherwise turns each tick's dispatchable candidates into `Agent()`/`SendMessage()` calls on its own hosted `'dispatcher'` session (`main/hosting/`'s `role` option). **The budget gate (#293) is the last pre-dispatch veto**, run through `dispatch/budget.ts`'s pure argument builders and `dispatch/budget-gate.ts`'s script runner — never a re-derived decision function, since the verdict is inseparable from the ledger I/O `bin/budget.mjs` itself owns. It drives the shipped script with its own `--session desktop` (never the cockpit's default log, so one sweep can never close the other's rows), resets once per process per repository, sweeps every pass, and gates every surviving candidate immediately before the send — a two-strike hold rule (`budgetRoute`, ported verbatim from `SKILL.md`) dispatches anyway on a second consecutive unreadable ledger, and an unrunnable or outdated script fails the whole repository's gate closed rather than dispatching unchecked. An `exceeded` verdict calls `main/actions/escalate.ts`'s `escalateToHuman` directly. **The observation pass (#292) is `considerRepo`'s own sibling step, independent of whatever dispatches that same pass** — `observe-pass.ts`'s `runObservationPass` (split out to keep this file under the 500-line limit) runs once `observableFrom(tick, drain())` is non-empty, for every ready repository regardless of whether anything else dispatches: it skips an item this process already wrote at or after the repository's current GitHub read (the read has not caught up yet), otherwise builds and runs the write through `main/actions/observe.ts`'s `applyObservation`, records an `ObservationRecord` (bounded to 20 per repository, the same idiom `DispatchRecord`'s own `RECENT_LIMIT` establishes), and — only on `applied` — updates the shared refresh memo (`refresh` records `{ sha, count }`, `refresh-stuck` clears it). A throw from one item's own write is caught and recorded `failed`, never a pass that stops partway through the rest of the list. `survived()`'s own re-read tolerates exactly one co-present role-bearing label for a `refreshBranch` candidate — the sanctioned pair `main/tick/plan.ts`'s own `actionableAndHeld` already allows — every other trigger keeps the original single-label rule. `turn.ts` is pure prompt/spec composition — `composeDispatchTurn`/`composeRelayTurn`, and `DISPATCH_PROMPT`/`REFRESH_PROMPT`, byte-pinned against the cockpit's own `pipeline/SKILL.md` prose, since both must send the identical instruction to a stage agent regardless of which one dispatched it. `select.ts` is the pure redispatch-floor (`REDISPATCH_FLOOR_MS`) and `confirmStarted`/`markUnconfirmed` logic deciding which already-sent candidates are still pending versus confirmed against the session's own task view. `ledger.record(` — the one write that actually counts a dispatch as sent — is called only from `dispatcher.ts`, and only after `confirmStarted` has actually seen the task start; `halt.ts`'s own `stopFor` (the dispatcher's per-item stop, called before each label reset) sits between `drain.set(` and `applyItemAction(` in that file for the same reason `drain.set(` itself runs first — resetting a label before the app's own agent is asked to stop would leave it working past the point its label says it is gone. `runtime.ts`'s `createDispatchRuntime` bundles the ledger, the unknown-streak map (`main/tick/ledger.ts`'s `createUnknownStreaks`), and the dispatcher behind a `bindWatcher` late-binding indirection, resolving the circular dependency between the dispatcher (which must call the watcher's own `republish()` on every change) and the watcher (which needs the dispatcher's own `status()` for its `dispatchStatus` param) without either module importing the other. The `desktop-dispatch` layer 1 check pins the module's existence, `shared/dispatch/`'s I/O-free boundary, the absence of `running`/`alive`/`isLive`, the `.actionable` gate rail (read only by `dispatchable.ts` and the pre-existing `main/trajectory/log.ts` reporting path), the single `gate: 'open'` literal, `resolve.ts`'s `DISPATCH_COMMANDS` reference, `halt.ts`'s own `drain.set(` -before- `stopFor(` -before- `applyItemAction(` ordering, `dispatcher.ts` calling `readGateClaim(` and naming the `'dispatch'` scope, `ledger.record(` appearing under `main/` only in `dispatcher.ts`, `DISPATCHER_MODEL` declared exactly once, `turn.ts`'s two prompts appearing byte-identical in `pipeline/SKILL.md`'s Dispatching block, the literal `'budget-unported'` appearing nowhere under `apps/desktop/src/`, `dispatcher.ts`'s own `fetchItemsByNumber(` -before- `budget.check(` -before- `store.send(` ordering, and `budget.ts`'s `BUDGET_VERDICTS`/`BUDGET_SESSION`/`OUTDATED_SCRIPT_SENTINEL` each pinned against `bin/budget.mjs`'s own `verdict()`, `sessionLogName()`, and unrecognized-argument wording. Three further pins (#292): `.observations` is read under `main/` only by `main/tick/dispatchable.ts`'s `observableFrom`; `dispatcher.ts` calls `writeObservation(` only after its own `owner !== 'app'` return; and `observation.ts`'s comment templates match `docs/FORMATS.md`'s "Approval withdrawn"/"Rebase required" fences and `TICK-PROSE.md`'s zero-diff escalation fence.

**`apps/desktop/src/main/hosting/` owns the full lifecycle of a hosted session (#98)** — the renderer only sends intents (eight `session:*` channels) and receives events (`session:event`, opaque; `session:status`, this app's own typed snapshot; `session:entries` (#219), the live projection's own narrowed delta). **`project.ts`'s `createSessionProjector` (#219)** turns that opaque stream into the same `TranscriptEntry` shape #83/#84 already derive on disk, reusing their own `createDeriver` rather than a second `tool_use`/`tool_result` pairing implementation (`shared/relay/`'s own three-renderers lesson, #123) — meta rows (turn complete, a denial, a retry, compaction) are built directly and interleaved into the deriver's own absolute index space through a translation map held only while a tool call is still open. `handle.ts` owns this projector: `send()` records the operator's own turn through it and moves phase `starting`/`ready` → `streaming` immediately, rather than waiting for a stream echo the CLI only sends with `--replay-user-messages`; `result` only drops back to `ready` when `queued_turn_count` is not a positive number, so a session with more already-queued turns stays `streaming` through all of them. `session:attach`'s ok branch carries this projector's own bounded window (`entries`, `firstIndex`, `partial`, `pendingSends`, `revision`) alongside the raw envelope replay, so a renderer reload rebuilds the live view from the same state a mid-stream `session:entries` push already describes. Streaming input mode, always: `input.ts`'s push-driven `AsyncIterable<SDKUserMessage>` is what keeps `interrupt()`/`setPermissionMode()` available for the handle's whole life, since a string prompt would silently disable both. `sdk.ts` is the third lazy Agent SDK seam alongside `sessions/sdk.ts` (#78) and `runtime/sdk.ts` (#97) — the only file here naming the package specifier, re-exporting `Options`/`SDKMessage`/`SDKUserMessage`/`CanUseTool`/`PermissionResult`/`PermissionUpdate` for the rest of the tree. `options.ts` is a pure mapping from `SessionStartMode` to `Options`; `sessionId` is never passed, so the `init` message stays the single source of `claudeSessionId` across all four start modes; `permissionMode: 'default'` plus `canUseTool` (#99) route every un-preapproved tool call through this handle's own permission broker rather than the CLI's own denial. `classify.ts` classifies a terminal transport failure over the four wordings the SDK actually emits (`classify.cases.json`, pinned by ENGINEERING §2), reusing `runtime/`'s own `classifyProbeFailure` for the diagnosis rather than a second failure vocabulary. `handle.ts` is one hosted session's phase machine and pump loop, appending every message to a bounded `REPLAY_LIMIT`-sized ring rather than a growing array — the on-disk transcript (#84) is the history, the ring exists only so a renderer attaching mid-stream is not blank. `fork.ts` states the fork UX decision: a fork is titled distinctly from its parent (through #78's own `createSdkSessionReader`, never a second reader) so #78's resumable list never shows two identical rows. `store.ts` is the process-lifetime `Map<sessionKey, Handle>` `main/ipc.ts` binds, `MAX_HOSTED_SESSIONS`-bounded on live handles only. This module may report a **process phase**, unlike `main/sessions/`, because it owns the child and holds the `Query` directly — a transcript on disk proves nothing, but a live handle's own state does. **`permissions.ts`'s per-session broker (#99)** turns every `canUseTool` call into a pending request on the handle's own snapshot — `pendingPermissions` rides the snapshot rather than a second event stream, so a renderer reload is never lossless-adjacent, and `grant.ts` narrows the SDK's own suggestions to an allowlist of three kinds, rewriting every kept update's `destination` to `'session'` — the renderer sends only an intent (`allow-once | allow-session | deny`), never a rule, and answering a prompt can never write `.claude/settings.local.json` or `~/.claude/settings.json`. The `desktop-hosting` layer 1 check pins the streaming-input-only rail (no string `prompt`), the absence of any direct process control (`node:child_process`/`node:fs`/`process.kill`/`.kill(`), the opaque `message: unknown` envelope, all four SDK wordings present in `classify.cases.json`, `SessionPhase`'s members against `handle.ts`'s own assignments (both directions), the absence of `running`/`alive`/`isLive`, `main/index.ts`'s `before-quit` calling `closeAll()`, `live.test.ts`'s own opt-in skip guard, the absence of `permissionPromptToolName` (mutually exclusive with `canUseTool`), the absence of `bypassPermissions`/`allowDangerouslySkipPermissions`/`'dontAsk'` alongside `options.ts` naming both `canUseTool` and `permissionMode: 'default'`, every `destination:` in `grant.ts` reading `'session'`, `permissions.ts`'s own `canUseTool` typed `Promise<PermissionResult>` with no `| null`, `project.ts` importing `createDeriver` from `../sessions` rather than re-deriving pairing (#219), and `\btool_use_id\b` appearing nowhere under `apps/desktop/src/` except `main/sessions/transcript-entries.ts` itself. **`persist.ts`'s `createHostingPersistence` (#103)** is `hosting.json`'s only writer — recoverable app state, not an operator-curated list like `registry.json`, so a missing or malformed file resolves to an empty state (`limit: DEFAULT_SESSION_LIMIT`) rather than refusing to load, and invalid `open` entries or an out-of-range limit are dropped individually. `save()` is fire-and-forget, skips a write whose serialized JSON already matches the last one written, and coalesces a save that lands mid-write to the newest state; `freeze()` drops every later save. `store.ts`'s `closeAll()` calls `persistence.freeze()` **before** closing a single handle, so the `closing`/`ended` phase quitting causes can never overwrite the very set this ticket persists. `store.ts` replaces `MAX_HOSTED_SESSIONS` with `DEFAULT_SESSION_LIMIT = 4` and `SESSION_LIMIT_CEILING = 8` — the operator's own setting, persisted, and lowering it never closes a session, only refuses a new start past the new limit. `start()`'s `already-open` refusal fails **closed**: a `resume`/`resume-at` whose `sessionId` already names a live (non-`ended`) handle's own `claudeSessionId ?? resumeTarget` is refused with that handle's own `sessionKey`, because two `claude` processes appending to one transcript is unrecoverable — a fork of an open session is still allowed, since a fork always gets a new id. `rate-limit.ts`'s `readRateLimit` narrows a `rate_limit_event` structurally, never importing the SDK's own event type; `utilization` is deliberately never read, since its unit is undocumented in the SDK's own types and a percentage in the wrong unit is misinformation. No `startup()` pre-warming: a warm child is a real process that counts against the limit, and its `Options` are fixed at spawn, so a wrong guess at the target repository and mode would waste a process against a shared quota. **`shared/hosting/label.ts`'s `sessionDisplayLabel`** is the one session display label, imported by both `renderer/src/session/rail.ts` and `renderer/src/permission/controller.ts` — the dialog and the rail would otherwise have no reliable way for the operator to tell which session a prompt belongs to. ## 3. Security

**Broad allow, authoritative deny.** The allowlist grants whole development-command categories; the deny list is the real safety surface for dangerous or interactive commands, and deny beats allow at every scope. Any permission change is reflected in both `templates/permissions.base.json` and PIPELINE.md's permission model section.

**The `PreToolUse` guard hook is the enforcement.** `permissionMode: dontAsk` in agent frontmatter stays as declared intent and a second line of defence, but has never been observed denying anything on its own (PIPELINE.md → "Why background dispatch needs care"). When a denial matters, the hook is what must change and what must be tested.

**The guard's rails are not subagent-only.** Two apply to any caller including the cockpit's own session, because the cockpit violated them under throughput pressure: no `gh`/`git` inside a shell loop, and no clearing `<labels.needsHuman>` unless a recent operator message names that item. A third denies plugin install or marketplace mutation from inside any worktree, since every scope resolves to the same on-disk `installPath` and would silently repoint every session on the machine.

**`sessionRequiredPaths` is a harness-level boundary no dispatched subagent can cross, and settings cannot grant it back.** A plan writing under those paths routes to `/port:implement` in an operator session; it is never worked around.

**A hook returns immediately outside a port-managed repository.** Installed at user scope the plugin loads in every session, so without that guard, installing it changes behaviour in every unrelated project on the machine.

**A hook records a harness decision; it never re-derives one.** Re-implementing permission matching inside a hook drifts from the original and reports what the hook *predicts* happened rather than what did.

**Known gaps are documented rather than silently tolerated:** shell redirection through an allowed command cannot be denied by pattern, because matching operates on parsed tokens while redirection is consumed by the shell; and a native `permissions.deny` match is not logged. "Write files with Write and Edit" is therefore a convention agents follow, not a technical guarantee.

## 4. Operator-facing completeness

The users of this system are operators reading GitHub and a terminal, so "user-facing" means every plan, review, comment, and cockpit line.

**Writing style, every output** (FORMATS.md → "Writing style"): bullets and short sentences over paragraphs, one idea per bullet · never restate context the reader already has, reference it · omit sections that do not apply, with no "N/A" or "None" filler · no meta-commentary about the document itself · say each point exactly once, never across body, inline, and summary.

**Every failure mode states, in writing, which direction it fails toward and why.** Both directions are chosen deliberately and neither is a default:

- `SESSION REQUIRED` detection **fails open** toward dispatch, because a false positive stalls an item forever and invisibly while a false negative costs one denied edit and a retry.
- The tick **fails closed on actions, never on reporting**: a blind tick dispatches nothing, runs no hygiene, resets nothing, and never claims "all clear" — but still schedules the next wakeup.
- The CI merge gate is **deliberately fail-open** on an unlabelled pull request, with the mitigations named upstream.
- A `CLAUDE.md` override **fails closed on the entry, open on the run** (#246): a refused line leaves the port default standing for that one field, reported, never silently applied — but a wholly malformed `port-overrides` block never aborts config loading, since a repository whose whole block is broken must still run on port defaults rather than halt.

**A blocked or denied action is reported exactly, never retried or routed around.** Emit `BLOCKED: <exact denied command + what you needed>` and stop; a denied command returns a hook decision with a reason, not a prompt.

**An absent signal is never read as a passing one.** An empty check rollup is pending, not green; a check with no conclusion has not passed. No verdict is formed while any check on the head commit is pending, or on a pull request GitHub reports `CONFLICTING`. Liveness is a `TaskList` call, never inferred from a label — an in-flight label means a stage *claimed* an item, never that anything is still running ("Liveness is a TaskList call, never a label inference"). The same rule holds for a GraphQL fetch: a non-zero `gh api graphql` exit is not evidence of no data — `gh` exits non-zero whenever the response carries `errors`, even when `data` is still usable, so the envelope is always parsed in full rather than trusted or discarded by exit code alone. Only the aliases actually named in `errors[].path` are treated as unavailable; every other alias in the same response is trustworthy. A GraphQL call is never filtered with `--jq`, since `gh` silently skips that filter on exactly the partial-error response this rule exists to read, and no code path returns an empty result set for a request that did not actually succeed (`desktop-github-adapter`).

**A denial log's line count is never presented as a denial count, and an unresolvable session id fails toward `unknown-session` rather than a guessed role** — the log's line total conflates real denials with allowlist misses and rail holds, and a wrong attribution is unrecoverable misinformation an operator would act on; both are pinned by the `desktop-local` check.

**A local transcript's recency is activity, never liveness.** Nothing readable from a file on disk proves a process is running — a crashed agent's transcript looks identical to a live one's, only older. `apps/desktop`'s session adapter therefore reports `lastActivityAt`/`activity`, never a `running`/`alive`/`isLive`-shaped field, and leaves "stalled" to a reconciliation that also holds the labels — the `desktop-sessions` check pins the absence mechanically. That reconciliation (`main/state/`) may report a stall, but a stall is a **report, never a proof** — `TaskList` remains the only real liveness evidence, and a session read that could not run never produces one, since a check that could not run is not a check that found nothing — the `desktop-state` check pins the same absence for the module that consumes it. **A stall is additionally suppressed when the evidence behind it is older than the poll that produced it** (#80 Decision 5): `shared/board/project.ts`'s `displayStatus` renders `stalled` as `stalled` only when the repository's GitHub source is healthy and its last read is within one poll interval plus a fixed grace window of `now`; otherwise it renders `in-flight`, qualified with the read's age. This fails toward under-reporting — a phantom stall costs one more glance, but training an operator to distrust the one signal this app differentiates on costs the whole feature. The app holds exactly one clock, in `main/state/watcher.ts` — the `desktop-board` check pins both the suppression's key set and the single-timer rail.

**A path is not evidence.** Reporting a derived fact means resolving it, not pattern-matching a string that correlates with it: the running-plugin tell resolves the install record's commit sha rather than printing a cache path, because the path-based version reported "stale" every time under a directory source ("Running-plugin staleness is resolved, not printed from a path").

**Large or fenced markdown never goes inline to `gh`.** Write the payload under `.temp/` and pass `--body-file` or `--input`; shell quoting of backticks and code fences fails cross-platform.

## 5. Accessibility

Narrow but real, because the pipeline's whole visible state is a set of GitHub labels.

**Label colour encodes role by hue and position by lightness.** Triggers blue, in-flight amber, gates red, terminal green, each an ordered Primer ramp in pipeline order, so position within a role is legible from colour alone. Gates step two shades at a time rather than one, "so severity reads from a large lightness delta rather than hue alone — legible under red-green colour vision deficiency" (`labels.json`'s own `$comment`). Every colour is a well-formed six-digit uppercase hex and no two labels share one ("Label colours are well-formed and distinct").

**Severity is never colour-only.** Review findings carry both an emoji and the word: 🔴 Critical · 🟠 Medium · 🟡 Low · ⚪ Nit.

## 6. Performance

**Cost is measured, then reduced, then pinned.** The polling tick collapsed from roughly 15 GitHub round trips to one aliased `gh api graphql --include` call at a measured ~12 points against the 5,000/hour budget, and layer 1 now fails if a per-label poll creeps back under the Tick procedure heading ("Collapsed tick query — one round trip, never a per-label poll").

**Polling adapts to whether anything can move without a human.** The pacing ladder holds at a 270s floor whenever something will progress on its own, and otherwise backs off one rung per consecutive no-change tick — 270 → 540 → 1080 → 1800 — resetting to the floor on any observed change. The cockpit **never stops scheduling wakeups**, because it is the only dispatcher unless the app holds the `dispatch` claim (#265) — and even then, gates, relay, and the cockpit-only writes still need this cockpit's own ticks, so a held `dispatch` claim never slows the ladder either. The constants and both preconditions are literal, checkable phrases ("Pacing ladder").

**No busy-waiting.** Bounded waits use a real timeout and a capped retry count; a bare `sleep`-shaped wait is a layer 1 failure ("No busy-waiting in the cockpit skill"). The next scheduled tick is how this system waits.

**Expensive work runs proportionally to what changed.** Layer 1 is free and runs on every pull request, across a three-OS matrix; schema validation and `apps/desktop`'s typecheck, lint, test and build run as their own jobs; layer 3 evals are path-filtered to prompt changes only. **Neither the evals nor the layer 2 audit may ever enter `commands.checks`** — that list is what `impl-agent` runs before pushing, so an eval there means every dispatched agent spawning its own model runs ("Behavioural evals never enter commands.checks").

## 7. Quality bar

**Comments state why, never what.** Every check block in `scripts/checks/*.ts` opens with the failure it exists to catch and, where one exists, its issue number. `labels.json` carries its entire colour rationale in a `$comment`. A comment restating the line below it has not earned its place.

**Small, focused files. No dead scaffolding, no transitional shims, and no placeholder content committed in anticipation of a later ticket.** A source file is at most 500 lines. Each exclusion below is mirrored one-for-one by an `exclude` entry in `scripts/checks/file-size.config.json`, pinned in both directions by the "File size limit" check:

- `pnpm-lock.yaml` — a generated index, never hand-authored.
- `schema/fixtures/**` — fixtures whose entire content is the thing under test.
- `plugins/port/bin/**` — every file there is copied alone into an adopting repository (§1), so the runner-plus-modules split is unavailable by construction. A permanent exemption, not debt, so it never enters the allowlist (#183).

An over-limit file outside these exclusions is split by topic, following the runner-plus-modules shape §1 describes for `scripts/checks.ts`. `scripts/checks/file-size.config.json`'s `limit` is this same number, checked by "File size limit and the shrinking ratchet"; its `allowlist` enumerates every file still over the limit with its exact current line count, as a ratchet — an entry may only be lowered, never raised, and removing a path from the allowlist is the definition of done for it.

**`scripts/` runs `noUncheckedIndexedAccess: false`, deliberately, unlike `apps/desktop`.** `tsconfig.base.json` turns it on for `apps/desktop`, where an indexed read crosses module boundaries and a bad index is a crash in the UI. In `scripts/` a regex-capture or `split(…)[n]` read sits either inside an `if (!m) { fail(…); }` guard or on an array the same function just built — the check's own `fail()` call *is* the error path — so a non-null assertion at every such site would add density, not information. `tsconfig.scripts.json` also sets `erasableSyntaxOnly: true` (rejects `enum`/`namespace`/parameter properties — exactly what Node's own type stripping cannot erase, so an unrunnable file fails in CI rather than at an agent's push) and `allowImportingTsExtensions: true` (import specifiers are the literal on-disk `.ts` path; Node never rewrites extensions).

**A check that cannot be made to fail is not a check.** Every validator pattern is asserted against both a passing and a failing example, using the real historical failure where one exists ("Artifact validator's patterns accept a good example, reject a bad one"). Every new rule is worth breaking deliberately once, to confirm it catches anything at all.

**A check must be able to distinguish the state it exists to detect.** `diff -rq` returned silence while both the cache and the checkout sat 42 commits behind `origin/dev` — a verification that passes in exactly the situation it was written to catch is worse than none, because it converts an unknown into a false assurance. Prefer a check whose failure mode you have observed.

**Every fixed regression leaves a mechanical guard behind, tagged with its issue number, and duplicated content leaves a mechanical pin behind, declaring no issue.** Layer 1 pins the literal phrase or contract that constituted the fix, so a future edit quietly reverting the reasoning fails in CI rather than in a live pipeline run. A prose-only fix to a prompt is incomplete; a `guard(#N): <one line>` marker declared on the check block that pins it — colocated, never a shared registry file — is the running record, rendered on demand with `node scripts/checks.ts --guards`. A duplicated copy gets the same treatment: a `pin: <one line>` marker on the check that asserts the two sides agree, rendered on demand with `node scripts/checks.ts --pins`.

**Rails are checkable preconditions, not bare prohibitions.** "Never do X" prose was violated twice under throughput pressure. A rail is instead shaped as something testable — `unblock #N` before a gate clears, "only when a check on it has gone red" before `approved` is removed — and layer 1 fails if either reverts to prose with nothing to check ("Cockpit rails stay checkable preconditions, not bare prohibitions").

**Component frontmatter is exact.** `name` must equal the file's basename for an agent and its directory name for a skill, and `description` must be non-empty ("Components parse and declare what they must"). A malformed component is *absent* from Claude Code's inventory rather than reported as an error, so nothing complains.

**Eval discipline:** one behaviour per case — if a grader needs "and", it is two cases · apply pressure, since a rule is only worth testing where following it costs something · grade the artifact, not the narration · name the failure the grader exists to catch at the top of the grader.

**Commit subjects are `#<issue> <imperative lowercase summary>`**, under 80 characters, no trailing period, `#0` when a commit genuinely has no issue. Write the message to a file and use `git commit -F <file>`, never inline `-m`, which collapses on Windows and drops the subject and co-authorship.
